# Implementation Plan

Please be mindful that Alpine is in CSP-safe mode.

## Core Features

- [x] Unify `#project`/`@tag` filtering on the Search page with the canonical parser - The Search page (`resources/views/search/index.blade.php`) has its own hand-rolled JS regex tokenizer (`parseSearchInput()`) for `#project-name`/`@tag-name`, duplicating logic that already exists server-side (in the spirit of `QuickAddParser`, the app's established single-source-of-truth pattern for this kind of token parsing). Eliminate the duplicate: route token resolution through the server-side parser via AJAX, the same way the quick-add live preview and date-preview already work (client sends raw text to the server, server returns the matched project/tags and the remaining plain text). Only the as-you-type suggestion dropdown (showing candidate project/tag names while a token is incomplete) may stay client-side, since that's a UI affordance, not authoritative matching — the decision of whether a completed `#token`/`@token` actually matches something must happen in exactly one place, in PHP. Confirm this fixes matching for multi-word project/tag names (e.g. "Home Renovation" typed as `#home-renovation`). Add/update a test covering multi-word names.
- [x] Audit project pickers for archived/done projects - Audit every UI element that lets a user choose a project to move or assign a task into (task edit form, quick-add `#project` matching, bulk-move, any others found by searching for project dropdowns/pickers). Confirm each is scoped to active (non-archived, non-done) projects only, consistent with `Project::forMember`/`activeForUser`. Fix any that aren't scoped correctly. List every file checked in the commit message, even if no bug is found in it.
- [x] Verify task/subtask project inheritance - Verify: (a) creating a task while viewing a project always sets that task's `project_id` to that project; (b) creating a subtask from the subtask tab on a task's page always sets the subtask's `project_id` to match its parent task's `project_id`. Fix any code path where either doesn't hold. Add/update tests covering both cases.
- [x] Relative date scheduling in the task date field - In the task date field only (not the quick-add bar), accept relative durations in exactly the form `[integer] [interval]` — a single non-negative-looking integer, a space, then one of `day(s)`/`week(s)`/`month(s)`/`year(s)`. The integer must be a positive whole number (1 or greater): `0`, negative numbers (`-3 days`), and fractional values (`1.5 weeks`) are all invalid input and should produce a clear error, not silently fail or resolve to something unintended. Input containing more than one interval (e.g. "one month, three days" or "1 week 2 days") is also invalid and should error — only a single `[integer] [interval]` is accepted, nothing compound. Forward-only (no past/"ago" support). Always relative to today's date, never to a date already present in the field. On successful parse, show the resolved date in the same live-preview `<span>` used for human dates today (e.g. "Saturday, September 12, 2026"), via the existing AJAX call to `POST /tasks/parse-date` (`TaskController::parseDate`) — extend `DateParser` rather than adding a second parsing path. Add tests for: each unit singular and plural, zero, a negative number, a fractional number, and a compound/multi-interval input — all except the plain singular/plural cases should produce an error.
- [x] Export the Overdue list to markdown - The Overdue list currently has no markdown export, unlike most other task lists. Implement it to match the Today page's export behavior: export only tasks currently visible under the on-page text filter (if one is active). The Overdue page has no separate incomplete/done/archived groupings to worry about folding — everything on it is incomplete by definition. Reuse the existing export mechanism/pattern from the Today page rather than writing a new one.
